# Plan: Spam-Detection Headers in Email View

## Goal

Show authentication and routing headers in the full-headers view (`ctrl+e`) so users can assess whether an email is likely spam: SPF, DKIM, DMARC results, Return-Path, and Received chain.

## Current State

- The current headers view only shows what's in the IMAP `Envelope`:
  `From`, `To`, `CC`, `Reply-To`, `Message-ID`, `Date`
- These are stored in `db.Message` fields
- Authentication headers (`Authentication-Results`, `Received-SPF`, `DKIM-Signature`, `Return-Path`, `Received`) are **not fetched or stored**
- IMAP fetch uses `Envelope: true` + `BodySection` — no `BODY[HEADER]` fetch

## What We Need

Email authentication headers that indicate spam/phishing:

| Header | What it tells you |
|--------|-------------------|
| `Authentication-Results` | SPF/DKIM/DMARC pass/fail from the receiving MTA |
| `Received-SPF` | SPF check result (pass/fail/neutral) |
| `DKIM-Signature` | DomainKeys signature (present = DKIM signed) |
| `Return-Path` | Actual bounce address (often different from `From`) |
| `Received` | Mail relay chain (hop count, origin IP) |
| `X-Spam-Status` / `X-Spam-Score` | Server-side spam filter score (if your MTA adds it) |

## Approach

### Phase 1 — Store raw headers during IMAP fetch

**IMAP fetch change** (`internal/imap/client.go`):
- Add `imap.FetchItemRFC822Header` (or `BODY.PEEK[HEADER]`) to the fetch options alongside the existing Envelope + BodySection
- go-imap v2 supports `&imap.FetchItemBodySection{Specifier: imap.HeaderSpecifier}` for fetching just the header section

**Parse change** (`internal/imap/parse.go`):
- Extract the raw header text from the fetched header section
- Parse out key headers using `net/textproto` or `net/mail`
- Store them as a JSON map in the `db.Message`

**DB change** (`internal/db/messages.go`):
- Add `Headers string` field (JSON blob) to `Message` struct
- Add `headers TEXT` column to the `messages` table (migration)

### Phase 2 — Display spam headers

**Header view update** (`internal/ui/model.go`):
- In the `renderMessageContent` function, when `contentShowHeaders` is true, parse the JSON headers blob
- Render spam-relevant headers in the same dimmed format, grouped or color-coded:
  - Green for `pass` results
  - Red for `fail` results
  - Yellow for `softfail` / `neutral`

**Example rendering:**
```
  Authentication-Results  SPF pass, DKIM pass, DMARC pass (example.com)
  Received-SPF           pass (sender.example.com: 192.0.2.1)
  DKIM-Signature         present (s=selector1; d=example.com)
  Return-Path            <bounce@example.com>
  X-Spam-Score           -0.5
```

### Phase 3 — Color-code auth results (nice-to-have)

- Parse `Authentication-Results` for `spf=pass`, `dkim=pass`, `dmarc=pass` etc.
- Render each result in green (pass) / red (fail) / yellow (softfail)
- Quick visual scan: all green = likely legitimate, any red = suspicious

## Risks

- **Storage size:** Raw headers can be large (especially multiple `Received` chains). Storing as a JSON blob might balloon the DB. Consider storing only the headers we display (auth results, SPF, DKIM, Return-Path), not the full raw header block.
- **Migration:** Existing users already have a `messages` table without the `headers` column. Need an `ALTER TABLE` migration.
- **Fetch overhead:** Adding a header section fetch to every IMAP sync increases bandwidth slightly. The header section is small (< 2 KB per message) compared to the email body, so this is negligible.
- **Dovecot vs Gmail:** Gmail may strip or modify some headers in IMAP responses. `Authentication-Results` should be present on both. Test on both accounts.
